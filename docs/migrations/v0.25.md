# Upgrade from v0.24 to v0.25

v0.25 adds typed tool inputs, host resources, model-call facts, and Stop progress observations.
It also changes the durable invocation and model-call ledger writers to v2. The released v0.24.0
reader rejects those v2 records, so choose the deployment and rollback path before resuming writes.

This guide describes the implementation integrated at `b27a15c` on 2026-10-28. Package metadata
still declares `0.24.0`; versioning, release artifacts, tag, and publication remain pending in the
[release audit](../V0_25_RELEASE_AUDIT.md).

## Identify the installation

For development examples, use Python 3.11+ and install the same checkout with
`python -m pip install .`, or install its built wheel. Run `examples/` from that checkout;
those files come from the repository. The report recipe is packaged and runs with
`python -m monoid_agent_kernel.reference.host_tool_report` after installation.

Record the source commit and wheel SHA-256 for every development build. Several development
builds report version `0.24.0`, including builds with different reader and writer capabilities.
Use the qualified v0.25 artifact and its matching documentation once the release is available.

## Update application code

- **Pydantic tool inputs:** `@tool` passes validated model instances, including nested models and
  models inside lists or dictionaries. Change `draft["title"]` to `draft.title` when `draft` has
  a model annotation. Choose a dictionary annotation when the handler needs dictionary access.
  Input serializers are skipped; invalid inputs retain `invalid_tool_args` and skip the handler.
- **Tool results:** top-level model results use `model_dump(mode="json")` semantics before entering
  the existing result envelope. Automatic conversion covers the top-level model. Return annotations
  add no validation or field filtering. Existing dictionaries, scalars, and explicit `ToolResult`
  keep their envelopes. See [typed tool compatibility](../COMPATIBILITY.md#typed-tool-source-compatibility-v025).
- **Host resources:** `host_tool_bindings` is optional. Supply fresh factories again after restore;
  keys and adapters have process-local identity. Set `inherit_to_children=True` explicitly when
  children or forks need fresh resources with the original authority chain. Child workspaces inherit
  the parent's effective operator policy, including constructor overrides. Follow the
  [resource recipe](../EMBEDDING.md#inject-host-resources-into-tools-v025).

When rolling a newly typed tool back to an older kernel, deploy a compatible handler together with
the kernel: accept dictionaries, call `Model.model_validate()` explicitly, and return
`result.model_dump(mode="json")`.

## Read call outcomes, usage, and Stop progress

Use `receipt.termination` to read `outcome`, `requested_by`, and `ended_by` independently. A stopped
call can finish draining a provider stream while retaining its cancelled outcome. Use
`receipt.usage_evidence` for explicitly reported counters and counter-specific completeness:
`no_dispatch`, `complete`, `partial`, or `unknown`. Explicit zero is a report. Missing facts stay
unavailable, including records from older writers and adapters without observation metadata.

Evidence covers kernel dispatches; provider SDK retries have their own accounting boundary.
Keep numeric `receipt.usage` as the existing accounting input. Provider reports describe observed
usage; the host reconciles charges with its billing source. Details and adapter integration are in
the [model adapter contract](../CONTRACTS.md#model-adapter).

Poll `termination_budget()` on the loop, runner, or retained `RunStream` for process-local progress.
`hard_cancel_remaining_s=0` means hard cancellation of the driver was requested; cleanup and durable
settlement can continue. Empty `calls` describes the owner's model calls. Tools, children, and
resource cleanup have separate lifetimes. Read the final receipt after cleanup for available usage.

Match execution ownership to the product: exiting a request-owned `astream` requests cancellation
and joins cleanup; closing a passive background reader releases that subscription. Explicit run
cancellation controls background work. See [stream ownership](../EMBEDDING.md#choose-who-owns-streamed-work)
and [Stop progress](../EMBEDDING.md#showing-stop-progress).

## Durable formats

| Artifact | New writer | Retained readers and recovery |
|---|---|---|
| Durable model invocation | `monoid.model-invocation.v2` | v1, its retained namespace alias, and v2 |
| Private `model_calls.jsonl` ledger | `monoid.model-calls.v2` | v1 and v2, including mixed files |
| Checkpoint | `monoid.checkpoint.v1` | Existing v1 envelope; its nested invocation can be v2 |

V2 adds optional `termination` and `usage_evidence`; v1 keeps its closed vocabulary. Current
readers preserve committed invocation payloads, hashes, and accepted aliases. New revisions use
the current writer. Existing records need no bulk rewrite, database schema change, or request
digest change. Preserve the original immutable records and content-addressed blobs.

Use `decode_model_invocation` when a custom consumer reads mixed invocation history.
`MODEL_INVOCATION_CODEC` retains its explicit v1 identity. Checkpoint's v1 outer identifier alone
does not make a checkpoint containing a v2 invocation readable by released v0.24.0.
The [compatibility ledger](../COMPATIBILITY.md#versioned-artifact-inventory) is the format inventory.

## Choose a deployment path

Inventory every reader of retained data, including recovery workers, custom validators, ledger
consumers, and backup/restore tools. Preserve a coordinated backup of run roots, shared metadata,
checkpoints, and referenced blob storage. Follow the [backup procedure](../PRODUCTION_OPERATIONS.md#backup-and-restore).

**Coordinated upgrade from released v0.24.0:** stop new admission and quiesce writers, take the
backup, then install the target build on all readers and writers before allowing new writes.
Canary an existing non-terminal checkpoint and verify its IDs, event position, pending tasks,
and referenced blobs before reopening admission.

**Reader-first rolling upgrade:** first deploy a verified build that reads v1/v2 while writing
v1 to every reader. The historical reader-preparation build is identified by:

- Source `74ff289431f203cb84595f90e0e09abfec12ee72`, integrated as
  `ec32ca8e2adc86354cfb9acd7cd5f3b9d657b537` in [PR #157](https://github.com/hoonseokyoon/monoid-agent-kernel/pull/157).
- Qualified development wheel SHA-256
  `ab8e726eb0a5c79b25264088e71c1e5f54424d5fd034a2ab25fbf75505f464b4`.

This is a source-identified development build. Its version string is `0.24.0`, and the published
v0.24.0 package lacks its v2 readers. Verify the exact artifact or qualify a later dual reader
against the retained v1/v2 fixtures and your storage adapters. Once every reader passes, deploy
the v2-writing target build. Retain the prepared reader and backup for rollback.

## Roll back safely

1. Stop admission and quiesce writers. Inspect the versions written since the upgrade.
2. After any v2 write, use the verified dual reader for a binary rollback. The prepared build
   preserves existing v2 coordinates and can write new v1 revisions. Those new v1 receipts omit
   facts; future readers keep that provenance unavailable.
3. Returning to released v0.24.0 after v2 writes requires restoring the coordinated pre-upgrade
   backup. Restore the stores as one recovery unit and preserve the upgraded copy for diagnosis.
   Rewriting v2 history into v1 would change immutable record identity.
4. Restore compatible tool handlers, resume one checkpoint, and verify a complete turn before
   reopening admission. Use the [rollback playbook](../COMPATIBILITY.md#rollback-playbook) for tokens
   and shared-store checks.

## Confirm the integration

Run the existing [typed tool](../../examples/custom_tool_quickstart.py),
[call facts](../../examples/model_call_facts.py), and [Stop](../../examples/termination_budget.py)
examples with the selected installation. For durable approval, follow
[prepare and resume in separate processes](../EMBEDDING.md#resume-approval-in-a-new-process): retain
the root and original run/task IDs, inject a fresh resource, and verify one approved read and the
original proposal after resume. The recipe also verifies that duplicate approval is ignored.

These checks exercise the documented integration paths. Qualify production adapters and your
transport's disconnect handling through the existing [embedding release gate](../EMBEDDING.md#conformance-and-release-gate).
